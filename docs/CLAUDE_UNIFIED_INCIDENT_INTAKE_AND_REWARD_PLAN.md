# 统一现场异常登记、留痕与奖惩匹配：实施方案

> 范围已更新：用户明确要求第一版实现后台自动记录与自动奖惩匹配，不需要主管复核。当前实施以 [CLAUDE_AUTO_INCIDENT_RECORDING_MVP.md](CLAUDE_AUTO_INCIDENT_RECORDING_MVP.md) 为准。本文件中的主管复核及审批要求不适用；自动匹配、结果留痕和持久待匹配任务仍在范围内。

日期：2026-11-04。基于当前事件台账、奖惩匹配、聊天与语音代码检查。本轮仅交付方案，未修改业务代码或业务数据库。

## 1. 建议方案

建立一个统一的事件受理服务，接收手动输入、语音听写、唤醒式语音助手和事件中心提交。每次明确的现场事件报告先落地为“待核对记录”，生成同一个 incident_id，再异步结构化、匹配候选条款和推进人工复核。

业务记录与匹配结果是不同状态。模型不可用或匹配失败不能导致现场报告丢失；候选匹配成功也不能自动变成人员奖惩决定。

第一版使用现有 SQLite 和模块化单体，在数据库内保存持久待办任务即可，不要求新服务器、消息中间件或多个 Agent。

## 2. 当前已有基础与缺口

- `core/incident_store.py`：事件编号、分类、风险、责任人、确认与结案状态，以及 incident_actions。现有记录以 task_id 唯一关联一次模型任务，不是完整的多来源/多次补充受理模型。
- `core/reward_penalty_engine.py`：使用实际规则返回候选及文档、版本、条款、页码。相关性分数不是经校准的适用概率。
- `core/reward_penalty_store.py`：奖惩记录存在同一个 incidents.db 的独立表，但没有完整的 incident_id / 事件版本 / 规则版本关联。
- `app.py:run_reward_penalty_match`：当前事件中心可以匹配并保存脱敏后的描述，普通聊天的三类输入尚未统一接入此流程。
- `IncidentStore` 当前排除自由原文，只保存有限事实和输入摘要哈希；奖惩表则保存脱敏描述。统一登记时需明确持久化字段，不能把所有聊天原文直接写进审计日志。
- `audit/audit_logger.py`：日志以元数据与哈希为主，不应替代可查询的业务记录，也不应承载业务原文。
- `core/voice_dialogue.py`：只负责最终转写及安全检查，提交聊天由前端完成。ASR partial、唤醒事件、TTS 播放事件不能直接触发事件写库。

## 3. 三种接入方式

### A. 显式现场记录模式：推荐第一版

输入区提供“现场记录”模式；听写填入该输入区，语音助手理解“帮我记录一件异常/补充刚才那件事”等命令，均调用统一受理接口。

进入记录模式后，用户每次提交明确的报告即可后台建立待核对记录，不要求填完整表单，也不要求每次再点一次保存。缺少关键事实时，已经保存的记录继续存在，再追问必要字段。

普通咨询、写作、假设和示例不因包含“异常、处罚、违规”便自动入正式台账。

### B. 普通对话自动发现事件：第二版增加

识别 report_incident / supplement_incident / correct_incident / hypothetical / general_question 等意图。对明确的实际报告建立可见的待核对草稿；证据不足或可能是案例演示时先澄清。

该能力需要真实中文评测和误记录率指标。不能仅凭关键词或模型自报 confidence 决定保存；用户要看到“已建立待核对记录”的反馈，并能标记误记。

### C. 结构化表单：保留为校正入口

从自然语言提取结果自动填表，供用户校正时间、区域、人员类别和证据。无需让所有用户先填写表单，但监督复核时应能看到并修改这些字段。

建议 A + C 先交付，随后在明确范围内加入 B。

## 4. 统一输入协议

定义规范化 Submission，不让三套输入各写一套数据库逻辑：

```text
submission_id         本次逻辑提交的稳定 ID，网络重试沿用
incident_id           新建时由服务端生成，补充/更正时引用既有事件
conversation_id      当前独立对话
source_channel       manual / dictation / voice_assistant / incident_form
source_message_id    对应用户提交消息
source_revision      输入/转写最终版本及是否经过人工编辑
operation            report / supplement / correct / retract_request
text                 用户确认提交的文字或 ASR final
attachments          具有访问权限的证据 ID
client_captured_at   客户端时间，仅作来源信息
```

actor、服务端接收时间、可访问区域和权限必须由认证上下文取得，不信任客户端传入的用户名或角色。

语音听写经人工编辑后提交时，保留 edited 标记及真实来源；不假装提交文本就是原始 ASR 输出。不要在 textarea.change 每次变化时登记。

## 5. 保存流程与可靠性

1. 认证、权限、长度、安全检查，识别明确的登记/补充目标。
2. 构造允许保存的脱敏报告快照及有限事实。缺时间、对象等字段时保留未知值，不要求模型补造。
3. 在一个 incidents.db 事务中写入事件/新版本、提交来源、创建操作记录和待处理任务。
4. 提交成功后向前端确认 incident_id、版本、待核对状态和后台匹配状态。事务未成功不得说“已记录”。
5. worker 获取待处理任务，进行事实结构化与奖惩匹配，分别持久化成功/失败和重试信息。
6. 界面更新关联记录卡片；语音只播报简短真实结果，不把“已入队”说成“匹配完成”。

模型/网络不可用时，只要本机事件存储可用，明确登记的报告仍可先保存，结构化与匹配待重试。数据库无法写入时明确提示未保存并保留草稿；不以聊天成功冒充记录成功。

后台任务放数据库持久表，采用与业务记录同事务的 outbox 思路。无需部署消息系统：worker 可直接轮询该表。不要只用 daemon thread 或内存队列，否则重启可能丢任务。

事务应短，不在事务内等待 ASR、模型或网络。现有各 Store 方法分别开连接，不能简单顺序调用它们便宣称实现了跨表原子写入；需要共享连接/工作单元。

worker 包含领取租约、超时恢复、重试次数和退避；默认按可能重复执行设计，以数据库唯一约束和条件写入确保幂等。

## 6. 数据关联与版本

以 incident_id 为聚合主键，在现有表基础上用新迁移增量添加字段或关系表，不新建一套平行事件中心，不修改已执行的 baseline。

建议包含：

- 事件主表：当前版本、登记状态、现有处置状态、创建人、区域、时间、当前结构化事实、脱敏叙述。
- incident_submissions：来源、submission_id、消息/对话关联、最终文本快照或受控文本引用、输入摘要、创建人/时间。
- incident_revisions：每次事实更新的快照、前后差异、源提交、修改者、原因与版本号。
- 现有 incident_actions：登记、补充、更正、认领、复核、退回、确认、作废/恢复等时间线，不物理覆盖历史。
- 奖惩匹配批次：incident_id、incident_revision、ruleset_version/hash、matcher_version、执行状态、候选及缺失条件。
- 奖惩人工决定：对应事件版本和匹配批次、采用/不采用及理由、复核人和时间；与处置结案分开。
- 后台任务：任务类型、去重键、事件版本、规则版本、attempt、租约、下一次重试时间和安全错误类别。

一个事件可以对应多个提交、模型任务和匹配批次。当前 task_id UNIQUE 不应继续承担所有这些关系，需设计兼容映射与历史记录展示，不能直接删除旧约束而失去旧数据关系。

登记状态、处置状态、匹配状态和奖惩复核状态分开维护，不把“匹配完成”等同“事件结案”或“处罚通过”。

## 7. 幂等、更正与合并

- 对 actor + submission_id 设置唯一约束。重试必须返回同一受理结果，不新增事件和奖惩记录。
- 同一提交不同内容时报告版本冲突，不能静默覆盖。
- 补充“刚才那件事”必须从当前会话中的真实事件 ID 解析；多件事件无法确定时追问。
- “不是三楼，是二楼”“刚才识别错了”更新同一事件，创建新版本并重跑匹配，旧匹配标记为过期但保留。
- 相同文字不作为全局唯一键。不同日期真实发生的相同异常可以分别登记，用户主动“再记录一件”应产生新记录。
- 多人上报同一现场事件属于业务去重，可以提示合并候选，但保留各自提交与来源；不能自动抹掉重复上报证据。
- 任务结果提交前检查事件版本。旧 worker 晚完成时，不能覆盖新版本的当前结果；可以归档为历史批次。

## 8. 事实和奖惩适用条件

事实至少区分：报告者陈述、用户已核对、工具证据、模型推断。事件记录代表“有人报告了此事”，不是已经查证属实。

建议字段：发生时间、报告时间、地点、人员类别、行为、发现/处置人员、已采取措施、结果、影响、违规次数、证据引用、缺失信息。

- 使用 Asia/Shanghai 解析“今天/昨晚”等表达，并记录来源与解析依据；没有发生时间时保留未知，不能用登记时间冒充。
- 人员类别、审批状态、违规次数、损失与后果必须有事实依据。未查到历史记录不等于“首次违规”。
- 区分“被拦截未进入”“已经进入”“已纠正”“否定/假设”等不同事实。
- 奖励与处罚可分别对应不同主体，不能因为一段话包含“发现异常”就认定高等级奖励，或把整件事件的所有人员视作受罚对象。
- 使用现有规则引擎和受控条款；模型可辅助提取事实、解释差异与生成追问，不能创造条款、金额或处分档次。
- 候选引用保留 document_code、version、clause_no、source_page、rule_id 和匹配原因，区分已满足/待确认/不满足的适用条件。
- 规则相关性分数不叫“处罚概率”或“准确率”。条件不足则显示“候选参考，需补充事实”；无匹配、规则缺失和执行失败分别显示。
- 事件纠正、规则更新后重新匹配时，保留当时的规则快照/内容哈希，避免只记录一个会变化的当前 JSON 路径。
- 人工复核采用或拒绝候选并说明依据；不自动扣分、罚款、处分或发放奖励。

## 9. 业务记录与审计边界

用户请求明确包括事件后台记录，可以为事件登记保存必要的脱敏事实和叙述，但不把所有日常聊天、ASR partial 或环境声音永久保存。

- 普通技术审计继续只存元数据和引用 ID。事件业务表承担可查询内容，权限、备份、导出和保留期限按事件数据管理。
- 原始完整文本、个人身份信息、原录音如确有业务需要，应单独选择保存范围、访问角色和期限；默认不保存原录音，不自动扩大原文落库范围。
- 报告被安全检查拒绝时不能绕过限制保存敏感原文，可以记录不含原文的拦截元数据。
- 使用白名单字段与输出校验，而不是仅靠排除 description/raw_text 等少数键防止自由原文泄漏。
- 所有修改追加版本和操作，默认不物理删除事件；误识别通过作废/撤回流程留痕。
- 创建人、复核人、时间与原因从可信上下文记录。查看、导出、修改分别控制，不能仅靠前端隐藏按钮。
- 输入哈希有助于关联或校验，但不能还原事实，也不能单独证明数据库不可篡改。若以后需要更强防篡改，另行加入独立校验、签名和受控副本，不在首版虚称已实现。

## 10. 页面与语音反馈

同一事件在聊天和事件中心都展示同一个编号：

```text
已登记：INC-...（待核对）
发生时间：待补充 / 用户报告时间
地点、人员类别、行为、已采取措施：按报告提取
奖惩匹配：待处理 / 候选待核对 / 无匹配 / 失败待重试
操作：补充事实｜更正｜查看时间线｜查看候选依据
```

语音可说“已建立待核对记录，还缺发生时间，奖惩条款正在后台匹配”。后续只有在任务真正完成后，才说“已找到候选条款”。

未发出消息、ASR 中间结果、按下唤醒按钮、助手自己的播报、普通制度咨询均不创建事件。

后台事件中心支持按来源、日期、区域、人员类别、处置状态、匹配状态和复核状态筛选。每日/周报统计只用明确状态与版本，不把作废或重试记录重复计数。

## 11. 分批实施与验收

第一批：统一 Submission 和 incident_intake 服务；接通三个输入来源；先保存待核对事件；持久任务；真实 ID 回执；原有记录与匹配页面建立关联。

第二批：更正/补充版本、适用条件、匹配历史、主管复核和事件时间线；在已有规则引擎基础上增加事实完整性校验。

第三批：普通对话自动发现事件、多人重复报告合并候选、统计与报表；先测误记录与漏记录，再逐步扩大启用范围。

至少验收：

1. 手动、听写、语音助手各报告一次，均生成相同结构的事件与来源记录。
2. 同一提交重试多次、重复点击、接口超时重发，只产生一份事件和对应当前匹配批次。
3. 模型不可用、匹配抛异常，已经保存的事件仍在且状态准确。
4. 写事务中途失败，事件/来源/操作/任务不能出现半套记录；不提示保存成功。
5. 入队后重启恢复处理；worker 中途退出，租约到期可重试。
6. 纠正地点/人员类别后，事件版本递增；旧匹配不能覆盖新结果，旧内容可追溯。
7. 相同内容的独立真实事件可以分别登记，多人上报可关联而不抹掉来源。
8. 普通咨询、示例、ASR partial、TTS、取消的草稿不进入正式登记流程。
9. 无权用户不能查看他人事件、附件、奖惩候选或导出原文。
10. 条件不足、无匹配、规则缺失、执行失败分别呈现，不编造奖惩决定。
11. 人工采用/拒绝和作废操作均留 actor/时间/原因；旧操作无法被普通编辑覆盖。
12. 兼容现有 incidents.db 数据、迁移、备份和恢复；不要在生产数据库中做破坏性测试。

自动测试之外，用真实手机完成一次“帮我记录→追问补充→纠正→查询记录→主管复核”流程。报告具体结果，不用模型 mock 代替真实语音与事实抽取验收。
