# 异常事件模块精简建议与实施边界

日期：2026-11-04。基于当前 app.py、IncidentIntake、IncidentStore 和奖惩匹配实现检查。本次为产品与工程方案，尚未实施界面或业务代码改动。

## 产品定位

当前用户目标是：现场异常快速登记、自动匹配奖惩依据、以后能查清谁在何时记录或修改了什么。不需要主管复核，也没有提出调度派单、时限考核、自动扣款发奖的要求。

建议模块名称由“事件中心/事件处置闭环”收敛为“异常记录”。普通用户只需要完成三个动作：记录异常、查看记录、补充或修改。三种输入保留，共用同一后台流程。

## 对现有功能的取舍

| 当前功能 | 建议 | 原因及处理方式 |
|---|---|---|
| 手动输入、听写、唤醒式语音助手 | 保留并共用登记服务 | 输入渠道有实际用途，不应各自建立台账 |
| 事件处置表单与奖惩描述表单 | 合并为一个“记录异常”入口 | 同一个异常不用选择先研判还是先匹配 |
| 主管确认、退回、重新提交、确认结案 | 从新事件流程和操作界面移除 | 用户明确不需要审批；历史动作和状态仍可读 |
| 自动责任人建议、派单、SLA/响应时限 | 从本期主流程移除 | 与记录及制度查询无关；不能保留一个无人维护的处置承诺 |
| 多 Agent 制度研判、完整处置方案 | 不在登记后自动运行 | 只需保存与现有奖惩匹配，不应等待大模型生成额外报告；历史结果保留可读 |
| 风险分、紧急程度分、制度置信度、Agent 分工 | 从主界面移除 | 用户难以区分含义，检索分数也不能替代制度适用判断 |
| 事件台账、独立奖惩记录表 | 合并为一个“记录列表” | 一条事件内直接查看奖惩依据；避免两页内容不同步 |
| 事件编号输入框、手动复制编号查详情 | 移除日常操作要求 | 点击列表记录即可打开；编号在详情仍可复制 |
| 补充/更正两个操作及术语选择 | 合并为“编辑记录” | 展示当前完整正文，用户增补或修改后保存新版本并重匹配；内部版本机制保留 |
| 重新匹配按钮 | 按需要出现 | 正常保存/编辑自动匹配；失败时显示“重试匹配”，规则更新由后台批量/按需更新 |
| 条款原文、来源、版本、适用条件 | 保留，分层展示 | 主卡片提供结论与主要缺项，展开才看完整依据；不能裁掉可追溯性 |
| 修改与匹配历史、技术任务状态 | 历史折叠，技术状态留后台 | 不让用户理解任务租约、版本号才能使用；出错时仍能定位 |
| 复杂统计、报表、附件流程 | 本期不扩展 | 先验证记录和匹配质量；保留已有附件关联，不另造上传流程 |

“从主流程移除”不是直接删除数据库字段、历史事件或共享 Agent 模块。先核对其他业务是否依赖，保留历史读取兼容，再清理无调用的代码。

## 简化后的页面

页面只保留三个区域：

1. **记录异常**：一个描述框、语音输入入口、一个“记录异常”主按钮。明确保存后自动匹配，不需要第二次保存或单独发起匹配。沿用项目已实现的语音能力，不另建识别管线。
2. **记录列表**：时间、描述摘要、奖惩匹配状态；团队授权视图再显示记录人。支持按关键词、时间和匹配状态筛选，并分页或加载更多，不能只显示最近 20 条导致旧记录无法查找。提交成功自动更新列表，无需用户手动刷新。
3. **记录详情**：完整描述、记录来源、登记人/时间、奖惩匹配卡片，以及“编辑记录”和折叠的“历史记录”。采用单一详情面板或移动端详情页，不同时铺满三套表格。

聊天及语音中的登记回执链接到同一事件详情，不要求用户复制 INC 编号到另一张表单。

### 输入字段

- 唯一必填是有效的异常描述。语音只有口令而没有事实时追问，不保存空事件。
- 发生时间和地点提供折叠的可选字段；描述中已有明确内容时可作为待用户校正的值，无法确定就留空。
- 事件类型不要求现场人员先选，可后续标注。不能默认“人员闯入”让所有事件都落错分类。
- 登记时间、记录人、输入来源由系统取得；登记时间不冒充发生时间。
- 涉及人员类别、次数、后果等匹配条件缺失时，在条款卡片提示所缺信息；先保存记录，不强制连续回答一串问题才能建档。
- 若保留“已处理情况”，作为可选事实描述，不据此引入审批或自动结案流程。

### 奖惩结果展示

每条事件默认展示最相关的一条建议，但标注“还有 N 条候选”以便展开；多个候选存在不同适用前提时，不得伪装成唯一确定结果。

首屏显示：奖励/处罚方向、规则中的具体规定、制度名称与条款号、适用条件缺口。原文、出处页码和规则版本折叠展示。隐藏相关性百分比；保留可解释的匹配依据。系统只自动匹配，不自动执行扣款或发奖。

用户可见匹配状态保持清楚：匹配中、有匹配建议、需补充信息、未找到条款、暂时失败。后台继续区分规则未配置、任务失败与重试耗尽等真实原因；不得把这些状态都说成“无违规”。保存成功是单独的事实，匹配失败时记录仍在列表中。

## 必须保留的后台能力

- 服务端登录身份、读取/编辑权限与脱敏规则。
- 事件、提交来源、创建留痕与待匹配任务的事务一致性。
- 逻辑提交 ID 的幂等处理：一次失败重试沿用 ID，新的独立事件必须使用新 ID，不能按相同正文合并。
- 持久匹配任务、重启恢复、有限重试；这些不暴露为复杂用户操作。
- 编辑产生新版本，保留旧正文和旧匹配；迟到旧任务不能覆盖当前结果或状态。
- 规则版本和事件版本可追溯；制度更新重匹配不能覆盖成伪造的旧规则历史。
- 列表以 incidents 为主查询，再关联当前有效匹配批次。未匹配成功的事件也必须出现。

建议新页面直接读取权威事件及匹配批次，停止依赖另一份奖惩展示副本同步。既有 reward_penalty_records 中没有关联 incident_id 的历史记录，需要作为历史条目保留可查；不能仅切换查询后让旧数据消失，也不能自动把每条旧匹配都认定成独立现场事件。

## 代码位置与现有开关的陷阱

- `app.py:4135` 的 `visible=settings.show_incident_desk` 包含旧研判、人工闭环，也包含新台账、补充/更正和详情入口。
- `app.py:4237` 的奖惩参考区在该 Group 之外，并维护独立后台记录列表。
- 因此仅将 `LUX_SHOW_INCIDENT_DESK=false` 不能完成精简：它也会隐藏用户需要的查询和编辑能力。
- 应重新组织组件与事件绑定，把统一列表和详情移出旧研判区域，并取消新事件进入 `PENDING_CONFIRMATION` 的分支；历史状态保留可读。
- 多 Agent 模块可能被聊天或其他功能引用，清理前查调用，不能直接删 agents 目录。

## 实施顺序与验收

1. 先修复 `docs/reviews/20261104_AUTO_INCIDENT_REVIEW.md` 中的结果错版、提交去重、空口令和任务状态问题，或将修复作为本次重构的明确验收项。换界面不能掩盖数据错误。
2. 合并为统一登记表单、统一列表和详情，删除新流程的人工审批绑定，替换旧首页入口与文案；将编辑放到当前事件详情中。
3. 统一查询数据来源，保留历史孤立奖惩记录入口，再清理确认无调用的旧处理代码。不要直接删历史表或重置数据库。

验收要求：

- 手动、听写、语音助手登记均进入同一列表；无需审批，成功保存后即能查看。
- 用户不需要复制编号、选择 Agent、选择研判类型或再点一次匹配。
- 编辑保存自动重匹配，显示当前版本结果；故障和晚返回不会恢复旧条款。
- 新的同文事件能独立登记，网络重试不重复，A→B→A 修改可成功。
- 记录能跨重启查询；分页、搜索和日期筛选遵守权限，旧记录不会因最近条数限制或页面合并失去入口。
- 手机端可完成“语音记录→查看条款→编辑更正”；真实麦克风验收单独记录，不以 Python 测试代替。
