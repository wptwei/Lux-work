# 第一版：现场异常自动记录与奖惩匹配

日期：2026-11-04。用户最新范围：后台自动记录，并自动匹配奖惩条款；不需要主管复核。本文件取代此前综合方案的第一阶段要求；本次仅更新实施任务，未修改业务代码。

## 目标与边界

手动输入、语音听写和语音助手提交的现场异常，统一保存到后台可查询的台账，返回记录编号，并自动匹配奖惩条款，将结果关联到同一条记录。用户不需要再点保存、单独发起匹配或等待主管批准。

本期包含自动登记、自动奖惩匹配、结果查询与留痕；不做主管复核、审批流、复杂统计或自动执行扣款、发奖等动作。直接保存经过现有安全检查、脱敏处理的报告正文及来源；匹配所需但尚未提供的时间、地点、对象和事实不得由模型补造。

“后台自动记录”指提交后自动持久化，不是录下所有环境声音或把全部聊天自动归档。

## 三种输入的触发规则

- 手动输入：开启“现场记录”模式，点击发送后保存。
- 语音听写：最终识别文字进入输入框，允许编辑，点击发送后保存。
- 语音助手：已开启语音对话时，说“帮我记录：……”或进入现场记录模式；一轮有效 ASR final 提交后保存。只有“帮我记录”而无内容时，询问记录内容，不建立空记录。
- 普通问答、假设、案例、ASR partial、唤醒词及助手播报不直接写入台账。第一版无需实现普通聊天中的全自动事件发现。

三种输入调用同一个服务端登记函数，不分别实现保存逻辑。通过客户端生成并在重试时保留的 submission_id 防止重复提交。

## 保存内容与反馈

每条记录至少包含：记录编号、脱敏报告正文、输入来源、服务端登记时间、登录用户、conversation_id、submission_id。听写内容被人工编辑时记录 edited 标记。现场发生时间若未提供则为空，与登记时间分开。

用户身份由服务端认证上下文取得，不接受客户端自行指定记录人。保存业务正文不能沿用只保留哈希的技术审计方式；正文保存在受权限保护的业务表，技术日志只保留编号、动作、时间等必要元数据。默认不保存原始录音。

同步执行一个短数据库事务，写入记录、提交来源、创建留痕及持久化的待匹配任务；提交成功后才返回“已记录，编号 XXX，正在匹配奖惩条款”。保存本身无需模型参与，匹配在事务提交后执行。使用现有 SQLite 中的待办表及应用内任务执行器即可，不要求 Redis 或外部消息队列。

数据库写入失败时明确提示“记录未保存，请重试”，保留输入草稿。模型不可用不能阻止已经取得有效文本的报告保存。语音转写失败时提示重新说或改用文字，不保存空报告。

## 自动奖惩匹配

1. 复用 `core/reward_penalty_engine.py` 和现有规则库，检查实际加载的条款是否完整。无需强制通过大模型完成已有的本地规则匹配。
2. 匹配结果通过 incident_id 关联现场记录，同时保存事件版本、规则版本/内容摘要、匹配器版本、匹配时间。复用并扩展现有 RewardPenaltyStore，不生成无法追溯到现场记录的孤立结果。
3. 每个结果显示制度名称、条款号、原文、出处页码（来源缺失时明确标注）、奖励或处罚规定、匹配依据及尚缺适用条件。金额、分值、人员类别、次数、后果等以实际规则为准，不编造。
4. 自动区分“有候选条款”“信息不足”“未匹配到条款”“规则未配置”“匹配失败”。未匹配到不等于没有违规；系统异常不等于未匹配到。相关性分数不能直接称为适用概率。
5. 不引入“待主管确认”或审批按钮。结果自动显示为“系统匹配建议”；事实不足时标明缺什么，用户可自行补充，不以主管批准作为展示或保存的条件。
6. 不能仅凭关键词判断适用。沿用并验证现有事实条件检查，例如“已拦截未进入”不等于“已闯入”，报告人不自动等于违规人，发现问题不自动符合奖励条件，没有历史记录不自动证明首次发生。
7. 匹配失败保留现场记录，显示失败状态并支持重试；持久任务须有领取、超时恢复和有限重试机制，服务重启后能恢复未完成任务。按事件版本与规则版本去重，避免重试插入多个相同结果。
8. 补充或更正时保存新版本及修改留痕，自动重新匹配。旧结果保留历史并标为已过期；旧任务晚返回不得覆盖当前版本的结果。

页面先显示登记成功，再更新匹配结果。语音可先播报“已记录”，匹配完成后只在对应对话仍有效时播报简短摘要；不得因切换会话播报他人的记录或旧结果。

## 接入现有工程

1. 先读取项目 AGENTS.md，检查现有 IncidentStore、数据库迁移、认证、安全检查、聊天及语音提交链路。
2. 优先复用 incidents.db、现有事件中心及权限；通过新增迁移增加必要的正文、来源和去重字段/关系表，不修改已执行的迁移，不重置历史数据。
3. 新记录的登记状态为“已记录”，表示系统收到报告，不代表事实已经核实。不得默认进入“待主管确认”，不得把审批作为记录可见或保存的前置条件。既有历史事件状态保持兼容，新入口绕开复核流程。
4. 现有 task_id 唯一约束若要求值，为每个逻辑登记提供稳定关联；不得为了写入而强制先运行模型分析。
5. 增加最小查询列表：编号、时间、记录人、来源、正文摘要、匹配状态，详情展示关联条款及结果历史。复用角色权限，普通用户可查看自身记录，有既有授权的管理员可查看授权范围内记录；详情和匹配结果接口同样检查权限。
6. 提供简单的补充/更正入口，修改时追加版本与变更留痕，触发重新匹配，不能静默覆盖已登记内容。记录正文不写入普通诊断日志。
7. 对同一账号的 submission_id 建立数据库唯一约束：同 ID 同内容重试返回原编号，同 ID 不同内容报冲突。不同 ID 的独立报告即使文字相同也不能直接合并。

## 验收

- 手动、听写、语音助手各提交一条，均能在同一台账查询到正确正文和来源。
- 无任何主管确认步骤，数据库提交成功即可返回记录编号。
- 三种输入登记后均自动匹配，结果可在对应记录下查询，无需单独点击“匹配”。
- 使用实际规则验证可匹配案例、条件不足案例及无匹配案例；无规则与执行失败显示不同状态，不输出虚构金额或条款。
- 匹配失败不丢记录；任务重试及服务重启恢复不重复生成同版本结果。
- 补充或更正触发新版本匹配，保留旧结果，旧任务晚返回不覆盖新结果。
- 同一次提交因网络重试只生成一条；不同的实际报告可以内容相同。
- 刷新页面、重启服务后记录仍存在。
- 模型服务不可用时，手动记录仍能保存；写库失败时不出现“已记录”，输入仍可重试。
- 语音中间识别结果不保存；取消、空文本、普通咨询不产生记录。
- 未登录和无权限用户无法访问他人的记录；正文遵循现有安全检查及脱敏规则。
- 迁移保留旧记录，已有聊天、听写和语音对话功能不受影响。

交付实际代码、新迁移、必要的事务/重试/权限验证结果及三种输入的人工验收步骤。将“自动测试通过”与“真机麦克风验收通过”分开报告；不要宣称未执行的验收已经通过。
