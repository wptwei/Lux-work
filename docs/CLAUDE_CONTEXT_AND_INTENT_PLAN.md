# 给 Claude 的实施说明：上下文理解与意图识别改进

本说明基于 2026-10-30 当前源码和 `.env` 中非敏感模型配置。仅提出实施方案，本轮不修改业务代码。联网和语音代码已出现新改动，实施时以现有代码为基线，保留这些改动。

## 1. 已确认的问题

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `.env` | 本地模式，`OLLAMA_MODEL=qwen2.5:3b` | 模型能力需要与更强模型对比评估，但不能只凭参数规模确定误解原因 |
| `core/settings.py` | 默认 num_ctx=4096、history_turns=3、history_chars=1800 | 界面可见的长对话并未全部进入模型 |
| `core/chat_context.py` | 每条历史消息仅保留开头，默认上限 600 字；总历史限 1800 字 | 末尾约束、修改要求可能丢失；长消息时实际保留轮数可能少于 3 |
| 同上 | 用字符比例估算 token，历史预算不足 160 字时直接不带历史 | 长系统提示或长当前消息可令历史消失；估算不是可靠的硬性上下文保证 |
| `core/providers.py` | 历史对话拼成单个 user 字符串；原生 messages 只有 system + user | 用户话语、助手回答、证据的边界不够清晰；应恢复角色结构，但此项不能单独保证理解质量 |
| `core/library_retrieval.py` | `should_search_library` 是较宽的关键词门控 | 出现“制度、资料、文件”等词就可能触发文件匹配，需理解否定、动作和语境 |
| 同上 | 模型文件匹配输入只有 `message[:500]` + 候选目录，不含会话上下文 | “第二份”“刚才那份”“不要下载，解释一下”等请求可能缺对象或丢失后半句要求 |
| `app.py:enter_skill` | 返回新的仅包含专项提示的 history | 点击进入专项后，原有对话被清掉，先前素材和约束无法继续引用 |
| `app.py:respond` | 模式对应技能系统提示持续生效 | 旧专项可能影响新问题；需显式管理继续任务和切换任务 |

注意：关键词命中只是进入文件匹配的门控，不能据此声称每次都会被错误路由；已有模型 `other` 分支可能返回普通对话。需针对具体输入验证最后选择。

另有 `core/supervisor.py`：它按关键词和固定领域优先级分类，并用命中数计算 confidence。当前 `app.py` 通过事件处理入口调用 orchestrator，不能把它误说成主聊天统一路由。若改造事件路由，须区分“巡检/事件领域”和“整理/解释/处置动作”；其 confidence 不是校准过的正确率。

## 2. 总体改造方向

当前输入 + 当前会话有效历史 + 活跃任务状态 → 解析本轮动作及指代 → 选择能力/工具 → 取得证据或产物 → 使用带角色的上下文生成回复。

把“要做什么”与“谈论什么”分别识别。例如“解释门禁制度”是解释动作、制度对象；不能因出现制度两个字就直接交付文件卡片。“找到制度并总结”是两步操作。

不要先引入复杂多 Agent、向量数据库或微调。先解决历史丢失、任务状态和动作识别，再用相同输入对比模型。

## 3. 第一阶段：上下文与任务状态

### 3.1 原生消息与统一安全入口

- 为 providers 增加接受 `messages` 的接口，保留原字符串函数兼容周报等旧调用。
- 发送真正的 system / user / assistant 消息序列，不再把所有历史揉成单个 user。
- 当前用户原文必须完整保留；历史失败提示、生成中占位、界面装饰与不完整轮次仍不作为有效对话。
- 不得绕过 RedlineGuard。完整消息列表、摘要、任务状态、证据均受长度检查、输入扫描、外发脱敏和输出检查约束；角色不能因扫描或脱敏被打乱。
- 助手历史可能包含错误，不能升级为用户确认事实。工具证据和摘要注明来源，不放成能覆盖系统规则的高优先级指令。

### 3.2 活跃任务状态

每个登录用户的独立会话维护最小状态，例如：

```json
{
  "task_id": "会话内任务 ID",
  "action": "draft",
  "object_type": "notice",
  "constraints": {"max_chars": 300, "format": "paragraph"},
  "confirmed_facts": [],
  "active_artifact_id": null,
  "referenced_file_version_ids": [],
  "pending_question": null
}
```

- 保存当前目标、用户明确提出的约束、已确认事实、选中文件/产物 ID 与待回答问题。
- 事实和约束记录对应的源消息 ID，区分用户确认、工具证据与模型推断；不得让推断变成事实。
- 用户说“不是通知，是情况说明”时更新相应槽位；说“200 字，改成 100 字”时用新约束覆盖旧值。
- “换个问题/新任务”清除旧任务特有约束；“再简短一点”沿用当前对象；模糊指代有多个候选时才追问一个必要问题。
- 点击专项时明确开始新任务还是继续当前素材；不能悄悄删除界面全部对话。按任务组织上下文，避免旧专项提示继续支配无关新任务。
- 文件与产物只引用真实 ID，使用前重新校验归属、权限、版本及存在性，不能由模型猜路径或猜文件正文。
- 默认只在隔离的会话状态保存，有超时和重置；不要把原文、摘要等新写入现有只存元数据的审计/任务台账。

### 3.3 上下文预算与摘要

- 统一预算：固定系统要求 + 活跃任务状态 + 当前输入 + 必要证据 + 最近完整轮次 + 输出预留。
- 使用可用的模型 tokenizer 或保守预算；以 Ollama 返回的 prompt_eval_count 等元数据辅助校验。响应 token 数用于事后观测，不能冒充请求前精确计算。
- 传入实际 `num_predict`，不能在历史预算中永远用默认 1024，而请求却使用其他设置。
- 优先裁剪无关旧内容；不能默认每条只截开头，因为末尾常有“不要表格”“仅修改第二段”等约束。
- 若需要压缩，优先结构化提取用户约束与已确认事实，再配合近期原文；摘要中的每个事实保留来源。摘要失败时保留近期原文并说明缺失，不生成未经支持的记忆。
- 长文档放在独立文档上下文，按任务检索相关段落；不要反复把全文当作历史对话输入。
- 对话中被拒绝的敏感原文不能通过摘要重新进入模型；摘要同样受原有安全策略约束。

## 4. 第二阶段：上下文感知的意图路由

### 4.1 输出结构

意图模型只输出经过 schema 校验的结构，例如：

```json
{
  "action": "revise",
  "object_type": "notice",
  "relation": "continue",
  "source_scope": "current_artifact",
  "target_id": "由应用候选中选择的真实 ID",
  "missing_fields": [],
  "needs_clarification": false
}
```

建议动作枚举：chat / retrieve / explain / draft / revise / summarize / analyze / export / clarify。字段名称与枚举最终按实际能力收敛；不要输出系统尚未支持的能力。

- relation 区分继续、纠正、切换、新任务。
- source_scope 区分当前产物、本地资料库、公开网络和无来源需求。公网访问仍遵守服务器配置与用户选择，模型分类不能代替联网授权。
- 路由输入包含本轮完整必要内容、活跃任务状态和有限的相关历史。不要只保留本轮前 500 字；超预算时保留关键要求，并对缺失内容显式处理。
- schema 只保证结构，不能保证意图正确。模型自报 confidence 不作为可靠概率；是否追问结合缺失槽位、指代候选数、规则冲突和评测结果。

### 4.2 路由优先级

1. 明确的界面操作和精确命令优先，例如用户点击某文件下载；仍执行权限与安全检查。
2. 解析用户对当前任务的纠正、否定与延续，例如“不要查资料，帮我写”。
3. 多义请求用带会话状态的模型结构化判断，关键词只提供候选，不能直接决定最终操作。
4. 缺对象或目标冲突时追问一次，例如有两份候选文件却只说“打开那个”。清楚的指令直接执行，不每轮确认。
5. JSON 无效、目标 ID 不存在、能力不支持或模型服务失败时给出准确降级；不能默认把所有失败都当作文件检索，也不能声称已完成操作。

复合意图如“找到巡检制度并总结三点”可以先取文件再总结，但必须取得授权正文后才总结；仅有目录卡片时说明缺正文，不编造制度内容。

## 5. 第三阶段：同题模型对比与参数调整

- 先固定测试集和上下文，再比较当前 3B 与硬件能承载的更强中文指令模型；7B–14B 可作为候选规模，不保证任一具体模型更好。
- 不自动拉取大模型，不自动切换云端。先报告内存/显存、实际吞吐、量化、并发及语音同时运行的资源占用。
- 可在目标模型支持且内存允许时对比 num_ctx=8192 等配置，配合调整历史预算；只调 num_ctx 而仍限制 1800 字，历史不会自动变多。
- 扩大上下文增加内存需求；上下文容量与遵循能力分别测量，不能通过扩大窗口代替路由修复。
- 路由模型可使用低 temperature（如 0–0.2）提高结果重复性，必须通过评测验证；它不会自动修正错误意图。
- 同一套测试分别比较：原方案、新上下文、新路由、最后再换模型。记录增益来自哪里，而不是把所有改动一起上线后凭感觉判断。

## 6. 验收与可观测性

先做 30–50 条中文种子案例，再补充用户的真实错误案例，并保留未用于调提示词的测试集。至少覆盖：

| 场景 | 输入例子 | 预期 |
| --- | --- | --- |
| 动作区分 | 帮我写一份巡检制度 | 撰写，不直接返回文件卡片 |
| 文件检索 | 找出我上传的巡检制度 | 找本人有权限的文件 |
| 否定 | 不要找文件，解释一下这个概念 | 解释，不能忽略否定 |
| 延续 | 上轮已有通知；本轮“改成 100 字，别用表格” | 修改当前通知，保留其他有效约束 |
| 纠正 | 不是通知，是情况说明 | 更新任务类型 |
| 指代 | 上轮返回两份文件；本轮“第二份” | 对应真实候选，不按文件名猜测 |
| 任务切换 | 上轮做周报；本轮“换个问题，帮我翻译” | 切换任务，不套周报格式 |
| 尾部约束 | 约束位于历史消息第 600 字以后 | 有效约束仍被保留 |
| 预算不足 | 长系统提示 + 长材料 + 追问 | 有明确裁剪策略，不静默装作记得 |
| 附件 | 总结刚才上传的 PDF | 取得对应权限内正文，不能只按目录总结 |
| 复合任务 | 找到制度并总结三点 | 取证后总结，证据不足说明原因 |
| 隔离 | 两个账号提问“刚才那份” | 不串用户或会话 |

记录意图混淆矩阵、错误工具调用率、指代成功率、约束保留率、完成率、追问率和延迟。先测基线再设改进目标，不能保证“识别率 100%”。

开发诊断默认只记录模型 ID、有效上下文配置、带入/裁剪轮数、字符数/token 估计、任务 ID、意图结果、选择理由类别与耗时。不要输出完整业务 prompt、推理链、密钥或用户原文。若需导出真实错误案例，采用用户明确提供的脱敏材料。

本轮尝试运行最小 Python 复现时，`.venv/Scripts/python.exe` 指向已不存在的 Python312 路径，未能执行。本说明中的问题依据源码判断，尚无模型 A/B 或运行回归结果。实施前检查/修复项目解释器，再运行相关测试；不要把这个环境问题当作上下文误解的既定原因。

## 7. 建议修改与交付

- `core/chat_context.py`：消息构建、统一预算、裁剪策略。
- `core/providers.py` 与 `core/redline_guard.py`：兼容 messages 的模型与安全入口。
- 新增 `core/conversation_state.py`：会话任务状态、约束来源、指代候选。
- 新增 `core/intent_router.py`：动作/对象/来源/任务关系识别及校验。
- `core/library_retrieval.py`、`app.py`：使用上下文路由；修复技能切换与历史生命周期；保留现有联网、语音能力。
- `core/settings.py`、`.env.example`：可配置预算与路由参数，不擅自修改用户模型配置。
- 测试：真实行为级上下文、路由、权限、安全脱敏和旧接口兼容检查，不只断言提示词包含某句话。

请按阶段实际实施，交付变更、回归结果、模型基线、对比结果与剩余限制；没有真实运行的部分必须标为待验证。
