# 给 Claude 的实施说明：联网知识获取与语音实时入框

编写日期：2026-10-30。根据当前仓库源码提出方案；本次未启动应用、未测试实体麦克风、未验证部署机器的搜索服务连通性。本文是实施任务书，功能尚未实施。

## 1. 目标与已确认的问题

在现有 Gradio 应用内完成两项增量改造：

1. 用户能主动联网查询公开知识，并得到有真实来源的回答。
2. 用户说话过程中，识别文字持续出现在当前可编辑输入框；停止后校正，可手动发送。

源码事实：

- `core/providers.py` 的模型入口是 Ollama / DeepSeek 对话接口，当前请求没有网页检索工具和工具执行循环。切换到 external 只改变模型调用，不能使当前实现自动搜索网页。
- `app.py` 的 `should_search_library()` / `retrieve_files()` 走本地资源库文件查找，不等于公网搜索，也不等于完整的文档正文问答 RAG。
- `frontend/voice_input.js` 已用 AudioWorklet 采集 PCM，每 2000ms 上传一批。
- `core/realtime_voice.py` 已能返回 partial 和 final，并处理会话、序号、尾段、重采样与过期结果。
- 直接影响实时入框的逻辑在 `frontend/voice_input.js`：`if (!result.final)` 分支只更新预览后 return；`setInput(input, combined)` 只在 final 时执行。
- `voice_asr.py` 当前固定 CPU + int8，默认 faster-whisper small；实际性能须测量。不能承诺改短定时器就能实现低延迟。
- `app.py` 把音频接收回执与 ASR 结果写到同一 voice_result 控件，应通过日志和浏览器实测检查事件覆盖、队列延迟或丢事件；这属于待验证点，并非已确认故障。
- `docs/ASSISTANT_ACCEPTANCE.md` 明确说明以前使用了 ASR 测试替身，没有完成实体麦克风和本地识别端到端验收。
- `healthcheck.py` 当前没有语音或搜索服务专项健康检查。

## 2. 实施顺序和范围

第一阶段：修复实时入框，沿用现有 PCM + Gradio 链路。

第二阶段：增加手动联网开关与搜索证据注入，默认关闭。先把开关、查询、引用与失败处理做通，再增加自动判断。

第三阶段：有实测性能证据后，再决定是否使用 WebSocket、流式 ASR 或更换模型。不要为前两阶段重构整个应用或引入完整 Agent 框架。

保留现有登录、资源权限、红线策略、技能、周报与交付流程。后续若开启自动搜索，周报/事件处置仍不默认混入公网事实；内部制度的适用依据继续来自受控资料。

## 3. 联网知识方案

### 3.1 数据流

用户提问 → 确认本次是否联网 → 外发查询检查与最小化 → 搜索 API → 标准化证据 → 预算裁剪 → 现有 guard.call_llm_stream → 带来源回答。

保留本地 Ollama 也能使用联网搜索。模型运行位置与是否向搜索服务发出请求必须分别配置和显示。

### 3.2 搜索服务选择

- 首个适配器建议 Tavily：有搜索与内容返回接口，便于先完成证据注入。实施前在目标 Windows 网络验证可达性、中文召回和账号额度，再确定是否启用。
- 若用户希望自建，后续可增加 SearXNG 适配器，需启用 JSON 输出。自建仍会把查询发给上游搜索引擎，并非完全离线；需要运维和可用性验证。
- 不通过直接抓取搜索结果 HTML 作为默认生产方案。

先只实现一个可用适配器，保留替换接口即可。不要在未验证时宣称某服务适合当前网络或可免费长期使用。

### 3.3 建议模块

- `core/web_search.py`：配置、超时、搜索适配、结果标准化、有限重试和安全错误。
- `core/web_context.py`：来源去重、证据裁剪、上下文预算、提示词与引用校验。
- `app.py`：联网控件、任务阶段状态、搜索调用与展示。复用现有聊天输出方式。
- `core/settings.py`、`.env.example`、README：补充配置。
- `healthcheck.py`：增加显式可选的联网检查，常规检查不得自动产生付费请求。

建议结构：`SearchResult(id, title, url, content, published_at, retrieved_at)`。published_at 可为空，不得以抓取时间伪装发布日期。

### 3.4 交互与路由

- 首版使用“联网搜索”开关，默认关闭；服务器总开关决定是否允许提供此功能。
- 开启后，用户这次发出的问题进入搜索流程；禁用、缺密钥、无权限时应明确显示原因。
- 后续可加“关闭 / 自动 / 开启”，自动策略综合时效需求、问题意图与当前会话；不能只看“最新”等几个关键词。
- 明确“查找本地文件”与“联网回答”两种意图的优先级，避免本地文件检索提前 return 吞掉明确的公网搜索请求。
- 状态展示为真实阶段：正在搜索 → 整理来源 → 生成回答。不得显示虚构进度。
- 搜索超时/零结果时明确提示“本次未取得联网资料”；需要时可继续给出标为已有知识的回答，但不能称为已联网核实。

### 3.5 外发与证据边界

- 搜索是独立外发通道。即使 `settings.is_external_model == False`，查询也必须先做外发检查；不能沿用“本地模型不脱敏”作为搜索策略。
- 首版优先使用用户本轮明确提出的公开查询。若需改写，只能在本地从允许外发的内容生成最小查询，并对最终查询再次检查。
- 不把整段历史、上传原文、内部制度、事件原文或敏感个人信息作为查询发出。命中 block / review 时在请求前停止。
- 网页文本属于不可信证据，不能覆盖系统指令、触发操作或要求读取密钥。不要拼入高优先级 system 指令中。
- 搜索返回的标题、链接和正文必须安全渲染，禁止执行原始 HTML。
- 审计延续现有元数据原则：服务、状态、时长、结果数、查询哈希；默认不保存查询、业务原文和完整网页内容。
- API 密钥只放服务端环境变量，不能进入前端、日志或错误详情。

### 3.6 内容与引用

- 初始建议搜索 3–5 条；根据模型上下文动态保留 2–4 条短证据，而不是把完整网页塞进提示词。
- 本地默认 `num_ctx=4096`，系统提示、当前问题、来源证据、历史、输出应统一分配预算；证据加入后重新压缩历史，不能只沿用现有历史预算。
- 先利用搜索 API 返回的可用正文/片段，不必首版增加任意 URL 抓取器。只有摘要时明确证据深度，不称为读过全文。
- 在提示词中明确：允许依据所附联网证据回答；缺证据则说明无法确认。与现有 SAFETY_SYSTEM 保持一致。
- 用服务端生成的来源 ID（如 S1、S2），正文引用 `[S1]`，文末显示对应标题、原始 URL 与时间。
- 服务端只允许实际返回且注入模型上下文的来源参与引用；不能接受模型自编 URL。
- 校验来源 ID 存在只是基础，不代表观点被证据支持。时效、数字和结论要能对应正文片段；证据不足时降低表述确定性。
- 涉及时效要求时使用当前日期和适当时间范围，优先权威来源；旧资料不得冒充当前有效资料。
- 如后续新增 URL 正文抓取，要限制 HTTP(S)、目标 IP、重定向、大小与超时，拒绝本机/内网/元数据地址，并逐跳校验，防止 SSRF。

建议新增配置（名称可按项目规范调整）：

```dotenv
LUX_WEB_SEARCH_ENABLED=false
LUX_WEB_SEARCH_PROVIDER=tavily
TAVILY_API_KEY=
LUX_WEB_SEARCH_TIMEOUT=10
LUX_WEB_SEARCH_MAX_RESULTS=4
```

## 4. 语音实时入框方案

### 4.1 核心行为

把输入框分为“用户原有内容 + 当前会话的语音内容区间”。partial 是当前语音假设的快照，下一次 partial 替换该区间；final 校正同一区间。不能每次追加整个识别结果，否则会重复。

可按以下语义实现，而非直接照抄变量名：

```text
录音开始：记录 voiceSessionId、受控文本区间、原草稿与修订状态
partial：校验 id/revision/ok → 更新本次语音区间 → 同步 Gradio 输入状态
final：校验 id/revision/ok → 校正本次语音区间一次 → 解除语音区间管理
取消：使本次会话失效 → 按选定语义回退本次语音区间 → 释放麦克风
```

### 4.2 防覆盖与状态同步

- 不仅修改 DOM：必须确认 Gradio 的组件状态同步，点击发送时后端收到的内容与可见文本一致。复用并实测现有 setInput / input 事件机制。
- 原草稿、光标外的手动输入不能被后续识别覆盖。
- 首版选择可解释且容易验证的编辑策略：录音中若用户手动编辑当前语音区间，立即停止自动替换该区间，保留手工修改；后续结果放预览供确认合并。不要做猜测性的字符串替换。
- 输入法组合输入期间不得打断组合或覆盖内容；识别结果先暂存，在组合结束后按区间所有权合并。
- 并发写入、光标移动、附件文本写入、任务重试与换页要有明确处理，不能只快照原草稿后反复覆盖整框。
- 处理最大字符数；超限保留用户草稿，提示分段。
- 取消默认移除本次自动管理且未经手改的语音区间，保留用户原文和手改；必要时停止自动更新并留给用户确认。文案必须准确反映实际行为。
- 已拒绝的 final 不得让前面 partial 静默成为“校验完成”；回退仍由程序管理的语音区间并明确提示。已经手改的文本保留，但仍要经过发送入口校验。
- 不自动发送、不抢焦点；录音期间发送操作应等待停止与校正，或明确结束录音后再允许发送，避免提交半段草稿。

### 4.3 复用与性能

- 保留现有 id、revision、seq、final 尾段处理、120 秒限制、权限和红线检查。
- 先实测现有 2 秒上传：首个文字时间、音频上传耗时、排队耗时、partial 推理耗时、停止到 final 耗时。
- 只有确认吞吐有余量后再尝试 500–1000ms 上传/调度，前后端设置背压，不要堆积每批完整重识别任务。
- 可以在显式启用语音后后台预热模型，预热状态可见；语音依赖缺失不能导致主应用无法启动。
- 当前 ASR 全局锁和 `concurrency_id='local_voice_asr'` 会限制多用户吞吐；先测并发排队，再决定是否需要独立 ASR worker / 资源限额。
- 当前取消主要依靠前端抑制迟到结果。补充服务端会话取消/失效信号，防止后续待处理任务继续浪费资源；运行中的推理如果不能安全打断，要丢弃结果并如实记录。
- Gradio 隐藏控件链路如实测出现丢事件，可先拆分 ack / transcript 通道；仍不稳定时再迁移到有鉴权的 WebSocket。

建议性能目标：预热后首字 1–3 秒、停止后 1–3 秒校正。它们是验收目标，不是对当前 CPU 的保证；须记录测试硬件与实测分位数。若现有 small 模型明显不达标，另行提出可配置模型或流式 ASR 对比，不能自动切换为云端上传音频。

### 4.4 浏览器与部署

- 本机先通过 `http://localhost:7860` 或 `http://127.0.0.1:7860` 实测。
- 同事通过 `http://192.168.x.x:7860` 访问不属于 localhost 安全上下文；应由反向代理提供浏览器信任的 HTTPS，并配置麦克风权限。不能靠改 ASR 模型解决浏览器采集被禁。
- 不建议以关闭浏览器安全限制作为正式部署方法。
- 加入检测提示：安全上下文、浏览器能力、系统/浏览器麦克风权限、设备占用、音量、后端回执和 ASR 状态。
- 取消、切页、隐藏、关闭页面均应释放音轨；支持范围和移动端行为需要实际验证。

## 5. 验收要求

### 联网

1. 关闭联网后不产生任何公网搜索请求；本地资源库仍可用。
2. 开启后，对需要近期资料的问题返回真实来源，回答结论能对应已注入的证据。
3. 密钥缺失、断网、超时、限流、空结果都有准确提示，不伪造联网成功。
4. 本地模型模式下，敏感查询也在搜索调用前拦截/脱敏；通过 mock 验证没有原文外发。
5. 网页提示注入、伪造来源 ID、危险链接不被当作可信指令或引用。
6. 小上下文配置不因检索内容挤满而丢掉系统约束和当前问题。

### 语音

1. 实体麦克风连续说 20–30 秒，停止前输入框已经持续更新；停止后全文校正且不重复追加。
2. 原有草稿、手动修改、中文输入法、取消、连续两次录音、迟到结果和字符超限都按约定处理。
3. final 被拒绝、长时间静音、尾音极短、权限拒绝、模型缺失、网络断开均有明确结果。
4. 点击发送时，后端获取的文本与输入框一致；不会自动发送。
5. 在本机和局域网 HTTPS 各做实测；至少两用户同时录音验证会话隔离和排队反馈。
6. mock / 合成 PCM 测试与实体设备实测分别报告，不能用前者代替后者。

复用并适当扩展 `tests/test_realtime_voice.py`、`tests/test_voice_input.py` 和现有前端检查。增加搜索适配、外发边界、引用校验及故障降级测试。修改后运行相关回归，不为所有旧功能重写测试。
