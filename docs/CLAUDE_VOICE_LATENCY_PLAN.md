# 语音输入提速实施说明

日期：2026-11-01。本轮仅检查源码、硬件与已有耗时元数据，没有读取录音或转写正文，没有修改运行代码或重启公网服务。

## 已确认的基线

- CPU：AMD Ryzen 7 H 255，8 核 16 线程；系统报告约 15.2GB 内存。
- 显卡：AMD Radeon 780M；未发现 NVIDIA 显卡。当前 faster-whisper CUDA 方案不能直接用于这块 AMD 集显。
- `voice_asr.py`：默认 small，设备固定 cpu，compute_type=int8；模型首次识别时加载；partial beam_size=1，final beam_size=3。
- `frontend/voice_input.js`：每 2000ms 上传一批浏览器原采样率的 PCM，以 base64 进入 Gradio 隐藏控件。
- `core/realtime_voice.py`：每次 partial 重新识别尚未提交的音频窗口；超过 16 秒后才尝试提交较早片段；final 重置 anchor/prefix 后识别整段录音。
- `app.py`：接收回执与识别结果共用 voice_result；识别共享 local_voice_asr 并发限制 1，模型另有全局锁。
- 当前启动日志的两次样本：10.61 秒音频，最终识别阶段 4.38 秒；2.22 秒音频，最终识别阶段 1.85 秒。它们不包含前端传输和 Gradio 排队时间，也不足以代表平均或高分位性能。
- 这两次样本只见 final 识别日志。尚未确认为何没有 partial 日志，不能直接归因为模型、网络或事件链丢失。

## 建议实施顺序

### 1. 先测量并确认中间结果真正返回

分别记录：客户端开始录音到首次文字显示、PCM 分批发送、服务端收包、识别调度等待、模型加载、模型推理、结果返回到输入框、停止到最终校正完成。

日志只保留会话匿名 ID、序号、修订号、音频秒数、各阶段耗时和成功状态，不保存音频、识别正文或业务提示词。

客户端和服务器的时钟不能直接相减计算单向网络耗时；端到端耗时用客户端自己的单调时钟，服务端阶段用服务端单调时钟。需将模型生成器完整消费时间算入推理耗时。

查明 partial 没有记录的原因：音频是否按 2 秒真正发送和收齐，receive/change/then 是否调度识别，recognize 是否返回 None，以及 ack/transcript 共用控件是否发生结果覆盖。事件链问题须以测量证据确认。

### 2. 在现有 Whisper 方案内做增量提速

- 增加显式的语音预热，避免用户首次说话时承担模型加载；保持懒加载兜底，语音依赖缺失不能阻止主应用启动。预热的资源占用需与 Ollama 同时运行测试。
- 上传周期作为配置，在 1000ms 与 500ms 间实测对比原 2000ms。不能只缩短定时器而堆积识别任务。
- 接收音频和模型推理解耦：每会话至多一个推理执行；推理期间累积新音频，下次用最新完整窗口，合并过时识别请求而不丢音频。保留全局资源限制，不能直接删除模型锁导致并发内存峰值失控。
- 若 ack/transcript 覆盖被证实，拆分传输回执和识别结果通道。
- 对稳定语音片段进行提交，并保留短重叠区间处理边界；停止后只校正未确认尾段，避免每次从头重跑全文。需要高精度全文复核时作为可选项。
- 稳定片段不能仅凭一次 partial 就冻结；必须验证更正、边界词、重复与漏字处理。
- 可评估“快速模式” final beam_size=1 与原值 3 的耗时和准确率；不能在未测量时宣称准确率不受影响。
- 可以将 base 与 small 作为可配置模型对比，前提是明确准备好相应本地模型。不要只改 LUX_ASR_MODEL 就让 local_files_only 的模型加载失败；不在用户录音时偷偷下载。
- 用相同中文样本比较识别错误率、岗位专有词、数字和时间。tiny 不作为默认推荐，除非准确率实测可接受。
- CPU 线程数应结合 ASR 与 Ollama 并行负载测试，不默认占满 16 个逻辑线程。

### 3. 减少公网音频传输开销

若浏览器实际是 48kHz，前端有状态重采样为 16kHz 单声道后再传 PCM，可将 PCM 数据量降至原来的约 1/3。不要简单丢样本或对每个块无状态重采样而产生边界失真。

需要覆盖 44.1kHz、48kHz、尾部残留、停止确认、乱序、丢包与取消。保留服务端兼容其他采样率的处理。

手机公网与电脑本机分别测量，区分隧道延迟和识别延迟。只有传输或 Gradio 事件链经测量确实成为瓶颈，再迁移到带现有账号认证的 WebSocket；更换协议本身不会缩短模型推理。

### 4. 若仍达不到体验目标，评估真正的流式中文 ASR

针对当前 CPU 机器，优先小范围对比 sherpa-onnx 中文 streaming Zipformer int8；另一个候选是 FunASR 的 paraformer-zh-streaming。它们是候选方案，不代表已在当前机器上验证更快或更准。

为 ASR 建立统一接口，保持会话级增量状态，返回 partial/final、修订号和错误；原 Whisper 保留为回退。模型状态不能跨用户共享。

不要将离线识别模型包装成每 500ms 重跑整段，便声称是原生流式。模型下载、引擎替换与现有依赖兼容应单独验证。

不默认切换云端语音。云端方案会使录音额外发送至第三方，需要单独说明数据路径并获得用户选择。

## 验收

- 使用一组脱敏、获准的中文真实语音，覆盖 3 秒、10 秒、30 秒和 60 秒，数字、岗位词及停顿；区分冷启动与预热后结果。
- 测试首字时间、停止到最终结果的延迟、P50/P95、错误率和资源峰值；先报告原版基线，再报告变化。
- 目标可先设为：预热后首字 1–2 秒、停止后 1–2 秒完成尾段校正。这是待验收目标，不是当前硬件性能承诺。
- 本机与手机公网各测；增加两用户同时录音以及 Ollama 同时生成的场景。
- 保留原草稿、手动编辑保护、输入法组合、取消、迟到结果、尾段、120 秒限制、红线校验和登录鉴权；不自动发送。
- 复用并扩展 tests/test_realtime_voice.py、tests/test_voice_input.py 和前端 PCM 检查，不能用 mock 替代真实性能测量。
- 当前公网服务继续运行。本轮只交付方案；实施后应安排一次重启，取得实际分享地址并重新做手机验收。
