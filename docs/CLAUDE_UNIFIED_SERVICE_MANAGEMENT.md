# 给 Claude：统一 LUX 服务管理

请在当前仓库实际实施下列改造。目标是在现有 Windows / PowerShell 5.1 环境中统一服务生命周期，消除重复启动、端口配置不一致、错误实例识别与隧道残留问题。本任务不需要购买服务器，也不更换业务框架。

## 1. 先阅读现有实现，复用公共逻辑

- `start_web.ps1`：目前加载环境变量后直接前台运行 app.py。
- `service.ps1`：目前是计划任务/登录自启使用的启动器，检查 HTTP 端口后运行 start_web.ps1。
- `deploy/LuxDeploy.psm1`：已有 Import-LuxEnv、Start-LuxService、Stop-LuxService、Get-LuxServiceState 等函数。
- `deploy/lux-restart.ps1`、lux-status.ps1、lux-health.ps1、lux-deploy.ps1、lux-rollback.ps1。
- `deploy/install-startup.ps1`、install-task.ps1 和 deploy.config*.psd1。
- `.env`：只读取必要配置，不把密钥或账号凭据写进输出。
- `logs/public-share-process.json`：此前临时公网实例的管理记录，可能与 logs/lux.pid 不同。
- 仓库中的 AGENTS.md 等适用约定。

已确认的问题：

1. 当前公网配置使用 7861，部署配置曾固定检查 7860；以实施时实际配置核对。
2. start_web.ps1 会用 .env 覆盖已有进程变量，而 Import-LuxEnv/service.ps1 的逻辑不同。
3. 部分管理函数只用命令行匹配 app.py 判断归属，不能可靠区分其他项目与 PID 复用。
4. service.ps1 把任意 HTTP 响应视为服务存在，无法区分“本项目正常运行”和“其他程序占端口”。
5. 本项目 venv 的 Windows Python 启动器与实际监听端口的 Python 可能是父子进程；隧道是另一个子进程。
6. git status 在当前执行身份下曾触发 dubious ownership；服务 start/stop/status 不应因为 Git 状态不可读就无法工作。不得全局关闭 Git 安全检查。

## 2. 一个对外入口

新增或整合为根目录 `lux.ps1`：

```powershell
.\lux.ps1 start
.\lux.ps1 stop
.\lux.ps1 restart
.\lux.ps1 status
.\lux.ps1 logs
.\lux.ps1 doctor
```

允许 `-ConfigPath` 等必要参数。status 支持 `-Json`，logs 支持有限行数；JSON 不包含密码、密钥、隧道 token 或原始业务内容。

管理入口只分发命令，生命周期实现集中在现有公共模块。原来的部署、回退、健康检查和自启脚本调用同一套逻辑，不能各维护一套进程管理代码。

保留旧入口兼容：日常用户继续执行 start_web.ps1 时也要进入受控 start，不再直接启动第二份。若保留前台调试模式，用明确的参数区分，仍执行实例检查。

区分外部管理入口与内部前台启动器，避免 start → service.ps1 → start 的递归。当前环境先确定一种主托管方式；若保留 Pid 与 ScheduledTask 两种模式，不能同时启用两个守护者。

## 3. 统一配置

- 配置优先级明确并只实现一次：显式命令参数 > 本次进程环境变量 > 指定 .env 文件 > 默认值。
- 全部入口共享该加载逻辑；保留 LUX_ENV_FILE、LUX_DATA_DIR、LUX_CONFIG_DIR、LUX_LOG_DIR 支持。
- 监听地址和端口以最终解析的 LUX_HOST/LUX_PORT 为准。BaseUrl 默认由它们生成；监听 0.0.0.0 等地址时，本机探测使用回环地址。
- 兼容现有 BaseUrl 配置，但检测冲突并明确报错，不允许静默检查另一个端口。
- 不自动改到下一个空闲端口掩盖冲突；应识别已运行实例或清楚报告外部占用。
- 当前账号库、强密码、业务数据库、文件权限、模型配置和公网分享开关均保持原意。

## 4. 单实例、状态和进程归属

- 用跨进程锁保护启动/停止/接管，覆盖两个终端同时 start；锁的作用域应包含规范化项目路径和服务实例，明确其与 Windows 用户/会话的关系。
- start 幂等：已运行且身份确认时，返回当前状态；不新起第二个进程。
- stop 幂等：已停止时正常返回。
- restart 必须等待旧实例真正退出、端口释放后再启动；超时则报错，不并行拉起新实例。
- 统一使用一个运行状态记录；原 logs/lux.pid 等文件如需兼容，由同一模块管理，不允许成为互相冲突的真相来源。
- 状态记录包含规范化项目路径、进程 ID/创建时间、启动器与监听进程关系、监听地址、端口、日志路径和最近的公网 URL/探测结果。原子写入，异常中断后可校验恢复。
- PID 文件不是唯一证据。核对进程创建时间、可执行路径、应用绝对路径、父子关系和实际监听端口，防止 PID 复用与误杀。
- 后续启动尽量使用 app.py 绝对路径，便于准确识别。
- 对旧实例命令仅包含相对 app.py 的情况，结合本项目 venv 启动器路径、父子关系和端口交叉验证；证据不足时标为 unmanaged，不终止进程。
- 停止时只处理确认归属于本实例的应用/启动器和 frpc 后代，避免残留隧道；不能按 python.exe/frpc 名称批量结束，也不停止其他服务共享的 Ollama。
- Windows 拒绝读取进程信息时，返回权限不足并说明无法确认归属，不把未知进程当作本项目。
- 后台启动使用隐藏窗口，退出码和日志可靠。不要依赖当前交互终端一直打开。

## 5. 状态和诊断

区分：stopped、starting、running、unhealthy、port_conflict、unmanaged、unknown 等必要状态。

status/doctor 应分别显示：

- 服务是否存在、归属是否确认、实际端口和日志位置。
- 本机 HTTP 是否正常；不能仅凭 HTTP 200 判断它是本项目。
- 本地模型是否可用。
- 公网分享是否启用、当前 URL，以及公网探测结果是否新鲜。
- 配置矛盾、残留状态、必要组件缺失和权限错误。

公网启用时验证登录页可达且仍要求认证；匿名访问受保护接口应被拒绝。本机正常而分享 URL 返回“No interface is running”时，标为公网故障，不能显示全部正常。

status 默认快速读取状态，不因不可用的外部网络长时间卡住；doctor 可以发起有超时的主动网络检查。进程运行不代表公网可用。失败的 HTTP 探测不等于应立即反复重启整个应用。

本批先实现准确诊断和受控启停；如加入自动恢复，应有重试次数、退避和人工 stop 的抑制机制，避免与用户停止意图或另一个托管器互相冲突。

## 6. 兼容发布与迁移现有实例

- 发布/回退脚本与新入口共享配置、进程识别和健康判断。发布失败不能因为另一个旧实例响应而误报成功。
- 修改自启脚本时检查现有入口，只替换明确属于 LUX 的自启项；不能全盘清理用户计划任务。
- 提供旧实例接管预览（例如 adopt -DryRun，或同等功能），只输出安全的进程证据，不泄露命令行中的 token。
- 先完成代码和隔离测试，暂不打断正在使用的公网实例。首次接管时展示已确认的目标和短暂中断影响，然后执行一次受控迁移。
- 接管后只保留一套托管状态，确认旧的同项目后台实例和旧自启入口不会再次拉起重复服务。若发现多个进程无法确认归属，停止接管并列出需人工核对项。
- 所有递归删除或移动先验证绝对路径，避免删除项目之外的数据。禁止用 git reset/checkout 或删除数据来解决端口问题。

## 7. 验收场景

实现必要的自动化测试，并在可运行环境完成以下行为验证：

1. 连续两次 start：只有一个监听实例，第二次返回已运行。
2. 两个终端并发 start：只有一个实例，锁正常释放。
3. 无关程序占端口：报告冲突，不终止对方、不改端口。
4. PID 记录过期或被复用：不误判、不误杀；正确处理残留状态。
5. stop 两次：均可合理完成，最终端口释放，属于本实例的 frpc 无残留。
6. restart：旧实例完全退出，再启动一份新实例，本地就绪通过。
7. 环境端口为 7861：监听、status、部署、health 一致，不再检查 7860。
8. Git 版本不可读取：生命周期和服务状态仍可用，只将版本信息标为未知。
9. 启动失败：返回非零退出码并指出日志；不能留下假 running 状态。
10. 本机正常、公网失效：状态能准确区分，保留账号认证。
11. 进程信息读取被拒绝：安全失败，不转而按进程名称批量结束。
12. 退出启动终端后：受托管后台实例继续运行。登录自启与“无人登录也能开机运行”的能力须分别说明并实测，不能混为一谈。

测试使用隔离状态目录、测试进程和测试端口，不终止实际用户进程、不更改实际业务数据。Mock 测试和 Windows 实机验证分别报告。
