# 自动记录与奖惩匹配：代码审查

日期：2026-11-04。范围：Claude 新增的统一登记、三种输入接入、自动匹配、版本留痕与查询。要求：不增加主管复核或审批。

结论：基础流程已实现，但存在会导致重复/漏记、更正失效和旧奖惩结果误展示的问题，建议修复后再验收。此次未修改业务代码、正式数据库或运行服务。

## 验证范围

- 已运行 `tests.test_incident_intake`、`tests.test_auto_incident_record`、`tests.test_reward_penalty`、`tests.test_reward_penalty_regression`、`tests.test_incident_store`，共 **40 项测试通过**。
- 额外在临时数据库运行 `docs/reviews/20261104_incident_repro.py`，复现了下面列出的 7 个后端异常场景。脚本使用虚构正文和匹配器测试桩，不调用真实语音或外部模型。
- 前端提交编号及清理事件问题通过代码检查确认，尚未在真机浏览器进行断网重发试验。
- 没有复跑 Claude 文档所称的全量 450 项测试；没有验证手机麦克风、制度原文的业务正确性或真实网络环境。

## 1. P1：更正失败后仍展示旧版本奖惩建议

位置：`app.py:1415`；`core/incident_intake.py:783`。

聊天提交后调用 `latest_match(incident_id)`，没有指定本轮版本，也不检查返回的 `stale`。若 v1 已匹配成功，v2 更正后匹配失败或仍在运行，该函数会返回 v1 的结果，聊天却将其展示在 v2 的回执下。

实际复现：数据库当前状态 `failed`，返回批次 `stale=true`，聊天仍含“系统匹配建议”，没有“匹配失败”。这是错误奖惩建议，不只是显示不及时。

修复：按回执的事件版本及当前有效匹配批次取结果；无本轮结果时显示本轮待处理/失败状态，旧结果只能进入标注过期的历史区域。奖惩记录页在新版本提交后也应标记上一版本过期，不继续将旧结果当成当前结果。

## 2. P1：前端重试未保留提交编号，失败后还会关闭记录模式

位置：`frontend/incident_record.js:30`、`:39`、`:74`；`app.py:4624`。

每次点击发送都在 `writeHint()` 中重新生成 submission_id。普通手动口令且未打开记录模式时甚至不传编号，由后端每次随机生成。因此“服务端已保存，但回执丢失，用户再次点击发送”会被识别为两次新登记。后端同编号幂等测试不能验证这一前端行为。

此外，发送链结束时无条件派发 `lux-intake:sent`，数据库写入失败被转成普通返回值，也会清除记录模式和来源。用户保留的草稿再次发送时，可能转入普通聊天而不再登记。

修复：为每次逻辑提交建立稳定 ID；失败和状态未知的重试沿用同一 ID，确认成功或用户主动发起新报告才更新。记录模式、来源、草稿只在明确登记成功后清理。补前端/集成测试，覆盖回执丢失、保存失败后重发和成功后再次独立上报。

## 3. P1：表单以正文哈希去重，导致独立上报遗漏、更正回退失效

位置：`app.py:2309`、`:2399`、`:2531`。

奖惩表单使用“账号＋正文＋日期”生成提交编号，事件处置表单同类处理。相同账号一天内两次独立发生的同样异常，无法分别登记。更正表单使用“账号＋事件＋操作＋正文”生成永久固定编号，使回退到曾经用过的描述不生效。

实际复现：

- 同一天两次独立表单调用，内容相同，最终只有 1 条事件。
- 初始事件后依次更正为 A、B、A，最后只有 v3，当前内容仍为 B；应为 v4、内容 A。

修复：使用每次用户提交生成的随机 ID，网络重试沿用，不能用正文作为提交身份。更新验收文档中“相同内容再次发送就应合并”的错误要求，增加同文不同事件及 A→B→A 测试。

## 4. P1：奖惩记录副本可能被迟到的旧结果覆盖

位置：`app.py:112`；`core/reward_penalty_store.py:57`；`core/incident_intake.py:1044`。

主表写匹配结果时检查了事件版本，但同步奖惩记录在独立回调中发生。回调虽然收到 incident_version，应用层没有向存储传递/校验它，upsert 也没有版本条件。旧回调迟到时可覆盖新结果。前台即时匹配与后台 worker 同时存在，使这种执行交错有实际入口。

实际复现：延后 v1 回调，完成 v2 更正和同步，再执行 v1 回调。事件当前正文为“南门……”，奖惩记录正文却退回“北门……”。

修复：尽可能从同一权威匹配批次查询结果；如保留副本，同步需带版本并在同一个写事务内验证当前版本，拒绝旧版本覆盖。副本同步失败目前只打印/吞异常，建议增加可恢复同步或查询时修复，避免任务完成但奖惩页长期缺结果。

## 5. P2：旧版本任务失败会覆盖新版本的成功状态

位置：`core/incident_intake.py:1065`、`:1078`。

成功结果写入有版本检查，但 `_finish_task` / `_retry_task` 的失败状态回写只按 incident_id 更新，没有检查事件版本或任务租约归属。

实际复现：v1 正在匹配，期间 v2 更正并匹配成功，然后 v1 返回异常。v2 的当前状态变为 `failed`，而 v2 最新匹配批次仍是 `candidate`。

修复：成功、失败、重试等所有状态写入都验证目标事件版本；任务结束还须校验领取者/租约令牌，防止过期 worker 改写其他执行者的任务。添加旧成功和旧失败迟到的交错测试。

## 6. P2：更新制度后重匹配覆盖旧批次且错误标注规则版本

位置：`core/incident_intake.py:868`、`:956`、`:1003`。

`retry_match` 重置旧任务为 pending，但保留其 ruleset_version / matcher_version。实际计算使用当前 matcher；保存则使用旧任务版本标签，并覆盖同一批次。重启后积压任务由新规则计算，也存在同类错标风险。

实际复现：先用 rules-old 匹配，再用 rules-new 重试。最终只有 1 个批次，批次标签是 rules-old，内容却是 rules-new 的结果，旧结果消失。

修复：规则/匹配器版本变化时新增对应任务与批次，保留旧批次；保证计算使用的规则与记录版本一致。若不保留旧规则快照，应明确迁移任务到新版本，不能把新计算结果写成旧规则结果。

## 7. P2：只有记录口令也能生成空业务记录

位置：`app.py:313`。

识别记录口令后若正文为空，`text=body or message` 又回退到完整口令，口令长度达到 5 字即通过保存校验。

实际复现：发送“请帮我记录：”，产生 1 条事件，保存的正文正是“请帮我记录：”。空的更正口令也有相同回退问题。

修复：显式区分解析出的正文与原始消息，命令正文为空时追问，不用口令填充业务内容；更正无正文不能生成新版本。增加标点、礼貌前缀以及纯标点输入的回归测试。

## 其他一致性问题

- 前端按钮提示仍是“登记为待核对事件”，与已确认的“已记录、无主管复核”口径不一致。应改为保存与匹配状态，避免让用户误以为还要批准。
- 既有多 Agent 事件处置表单仍显式写入 `PENDING_CONFIRMATION`（`app.py:2544`）。这不是历史数据兼容，而是该旧入口仍生成待主管确认的新事件。新聊天自动登记入口已经用 `RECORDED`，但若产品要求所有新登记入口都无复核，则旧表单也需统一；不要删除历史状态以免破坏旧数据。
- 失败重试耗尽后，统一文案仍称“后台重试中”，应区分会自动重试和需要用户重试。

先修 1—4，防止错用旧奖惩结果、漏记和重复登记；再修 5—7，补齐交错执行、规则变更和空口令测试。无需加入主管复核。沿用当前数据库和 UI，避免为修复重写全套流程。
